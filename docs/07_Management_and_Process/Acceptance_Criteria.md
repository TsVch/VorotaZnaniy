## 🎯 Core Philosophy

As CTO, I enforce **unambiguous, testable, and binary** Acceptance Criteria. 

- **Definition of Done (DoD)** is global: it applies to *every* task (e.g., "code is linted", "tests are written").
- **Acceptance Criteria (AC)** is local: it applies to a *specific* feature or task (e.g., "user cannot upload files larger than 500MB").

A task is **rejected** if even a single Acceptance Criterion is not met. There is no "partially meets criteria". 

---

## 📝 The Standard Format: Behavior-Driven Development (BDD)

To eliminate ambiguity for both human developers and AI agents (Freebuff), all Acceptance Criteria **must** be written in the **Given-When-Then** format.

### Structure
- **Given** [some initial context or state]
- **When** [an action or event occurs]
- **Then** [the expected, observable outcome]

### Why BDD?
1. **Unambiguous**: Leaves no room for interpretation.
2. **Testable**: Directly maps to automated test cases (Jest, Playwright, Pytest).
3. **Business-Aligned**: Focuses on user behavior and business value, not implementation details.

## 📋 Anatomy of a Task's Acceptance Criteria Section

Every Task Package generated by the CTO will include an "Acceptance Criteria" section structured as follows:

```markdown
### Acceptance Criteria

**AC-1: [Short Title of the Criterion]**
- **Given** the user is authenticated and owns the workspace
- **When** they submit a PDF file of 50MB via the upload endpoint
- **Then** the system returns a `200 OK` with a presigned S3 URL
- **And** a `document` record is created in the database with status `PROCESSING`

**AC-2: [Short Title of the Criterion]**
- **Given** the user attempts to upload a `.exe` file
- **When** they call the upload initialization endpoint
- **Then** the system returns a `400 Bad Request` with error code `INVALID_FILE_TYPE`
- **And** no database record is created
```

## 🛡️ Mandatory Criteria Categories

For every Task Package, the CTO will ensure Acceptance Criteria cover these four dimensions:

### 1. Happy Path (Functional)
Verifies the feature works as intended under normal, expected conditions.
> *Example:* Given a valid Stripe webhook, when `checkout.session.completed` is received, then an `access_grant` is created for the buyer.

### 2. Edge Cases & Negative Paths
Verifies the system gracefully handles invalid inputs, missing data, or boundary conditions.
> *Example:* Given a user with an expired access grant, when they request a document view, then the system returns `403 Forbidden`.

### 3. Security & Authorization
Verifies that the feature enforces the rules defined in [Security Requirements](../04_Security_and_Access/Security_Requirements.md) and [Authorization](../04_Security_and_Access/Authorization.md).
> *Example:* Given User A tries to access a document owned by User B's workspace, when they call `GET /documents/{id}`, then the system returns `403 Forbidden` (preventing IDOR).

### 4. Performance & Scalability
Verifies the feature meets the targets defined in [Performance Requirements](../06_Quality_and_Standards/Performance_Requirements.md).
> *Example:* Given a document with 100 pages, when the user requests page 1, then the presigned URL is generated in < 50ms (p95).

## 🚫 Anti-Patterns (What NOT to do)

| ❌ Bad Acceptance Criterion | ✅ Good Acceptance Criterion (BDD) |
| :--- | :--- |
| "The upload should be fast." | "Given a 10MB file, when the upload completes, then the total API round-trip time is < 500ms." |
| "Users can't see other people's docs." | "Given User A, when they request `GET /documents/{User_B_Doc_ID}`, then the system returns `403 Forbidden`." |
| "Make it look good on mobile." | "Given a viewport width of 375px, when the viewer loads, then all UI controls are visible and touch targets are ≥ 44x44px." |
| "Handle errors properly." | "Given the OpenAI API returns a 500 error, when a user submits a query, then the system returns `503 Service Unavailable` and logs the error." |

## 🔄 The AC Verification Process (CTO Review)

When Freebuff submits a completed task, I (the CTO) will perform the following verification:

1. **Map Tests to ACs**: I will check the submitted test files (e.g., `*.spec.ts`, `*.spec.py`) to ensure there is at least one test case explicitly covering *each* Acceptance Criterion.
2. **Manual Validation**: For UI/UX criteria, I will verify the implementation matches the expected behavior (or review the Playwright E2E test proof).
3. **Binary Decision**: 
   - If **all** ACs are met and tested → **ACCEPT**.
   - If **any** AC is missing, untested, or failing → **REJECT**. I will list the exact AC(s) that failed and require a fix.

## 📌 Key Takeaways for Implementation (Freebuff)

1. **Do not guess the criteria**: If a Task Package's Acceptance Criteria are unclear, ask the CTO for clarification *before* writing code.
2. **Write tests first (TDD)**: Use the Given-When-Then criteria to write your test cases before implementing the logic. This guarantees the criteria are testable.
3. **No silent failures**: If a "Then" condition is "return 400 Bad Request", ensure the error payload matches the [API Contracts](../03_Architecture_and_Design/API_Contracts.md) standard.
4. **Update ACs if scope changes**: If during implementation you discover a criterion is impossible or incorrect, flag it to the CTO. Do not silently ignore it.
